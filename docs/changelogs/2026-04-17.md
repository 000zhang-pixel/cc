本次修复两个生产问题：

## 1. 文案重复度修复

**问题现象：** T_260417_057 任务的 img01/img02/img03 三组标题均以「穿搭的温柔…」开头，正文叙事结构几乎一致。

**根因链：**
1. 三组 `content_type + platform + category` 完全相同 → 查到同一条 Strategy 记录
2. Strategy 的 `文案叙事节点` 成为所有组共享的叙事骨架
3. 生成时无篇次感知，LLM 默认沿用最熟悉的句式
4. 生成第 2、3 组时不知道第 1 组写了什么，无法主动回避

**修复：`middleware/handlers/content_generation.py`**

### 1a. `_build_text_prompts_from_strategy()`：加入篇次差异化指令

```python
# 新增参数
def _build_text_prompts_from_strategy(
    ...,
    group_index: int = 1,
    total_groups: int = 1,
) -> tuple[str, str]:

# 新增逻辑：按篇次轮转指定标题句式
diversity_block = ""
if total_groups > 1:
    _title_patterns = [
        "疑问句式（如：为什么我…？）",
        "数字/对比句式（如：买了X件才发现…）",
        "场景直述句式（如：健身/通勤/约会时…）",
        "反转/意外句式（如：没想到一条链子竟然…）",
        "情绪共鸣句式（如：那种感觉就是…）",
    ]
    this_pattern = _title_patterns[(group_index - 1) % len(_title_patterns)]
    diversity_block = (
        f"\n\n⚠️ 差异化要求：这是本产品第 {group_index} 篇笔记（共 {total_groups} 篇）。"
        f"标题请采用「{this_pattern}」，叙事切入角度必须与其他篇次明显区分，"
        f"禁止重复相同的开头句式或叙事骨架。"
    )
```

**效果：** Prompt 阶段强制结构差异，三组分别对应疑问/数字/场景三种标题模式。

```python
# 新增：预计算 C-suffix 组顺序
c_suffix_records = [pr for pr in prompt_records if pr["suffix"] == "C"]

```

### 1c. `_generate_content()`：追踪已生成标题，实时注入反重复指令

```python
# 新增：循环外初始化
prior_titles: list[str] = []

# 新增：生成前注入已有标题
if prior_titles:
    prior_block = "\n".join(f"  - {t}" for t in prior_titles)
    system_for_generation += (
        f"\n\n⚠️ 本批次已生成以下标题，新内容的标题句式和叙事角度必须与之明显不同，"
        f"禁止复用相同的开头词或句型结构：\n{prior_block}"
    )
text_result = text_adapter.complete(system_for_generation, c_prompt_text)
title, body, _ = self._parse_text_result(text_result)
prior_titles.append(title)  # 生成后追加
```

**效果：** 生成每篇时，LLM 能看到前面已有的真实标题，主动规避重复句式。

## 2. 部分图片失败静默通过修复

**问题现象：** T_260417_057 的 img01、img03 组各缺 img_03.jpg，但飞书状态显示"已生成"，下次触发任务直接跳过，缺图永远不被重试。

**根因：** 图片生成循环中，单张失败时只设了 `update["失败原因"]` 而非 `fail_reason`，导致 `if fail_reason:` 判断为 False，整组状态仍写为"已生成"。

**修复：`middleware/handlers/content_generation.py`**

### 2a. 部分失败改设 fail_reason

```python
# 改前
elif not fail_reason and failed_count > 0:
    update["失败原因"] = f"部分图片失败：{failed_count}/{img_count} 张未生成"

# 改后
elif not fail_reason and failed_count > 0:
    fail_reason = f"部分图片失败：{failed_count}/{img_count} 张未生成"
```

**效果：** 有图片失败时整组状态变为"生成失败"，下次触发任务会重试。

---

### 2b. 重试时跳过本地已存在的图片

```python
# 新增（图片生成循环开头）
img_filename = f"img_{idx+1:02d}.jpg"
if self._storage:
    local_img = self._storage.get_content_path(plan_code, gid) / img_filename
    if local_img.exists():
        logger.info("Image %d already saved locally for %s, skipping", idx+1, gid)
        attachment_tokens.append(f"__local__{img_filename}")
        continue
```

**效果：** 重试时仅生成真正缺失的图片，已保存的不重复生成，节省 API 调用。

## 3. 新增脚本

### `scripts/check_nanobanana.py`

检测 runapi.co/Gemini 图片接口是否可用，成功时发送飞书群通知。可挂 crontab 定期轮询。

```
用法: python scripts/check_nanobanana.py
退出码: 0=接口正常, 1=仍不可用
```

---

### `scripts/repair_missing_img.py`

补生成指定任务中缺失的图片，支持：
- 自动检测本地与飞书附件数量差异
- 本地已有文件直接补传飞书（跳过 AI 生成）
- 本地缺失文件重新生成后保存+上传

```
用法: python scripts/repair_missing_img.py <plan_code> <group_id> [group_id ...]
示例: python scripts/repair_missing_img.py T_260417_057 img01 img03
```
